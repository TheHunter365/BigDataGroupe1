Concept de Découplage & Buffering

💡 Résultat : Kafka absorbe les 1 000 ev/s entrants et les redistribue à 100 ev/s — aucune perte de données, aucune saturation mémoire.

L'intégration de Kafka entre la source de données et les moteurs de traitement répond à un besoin critique de Découplage et de Buffering. Si notre script Python ingère les données à une vitesse de 1 000 événements/seconde, mais que le système de traitement SE4 ne peut analyser que 100 événements/seconde, le système risque de saturer sans tampon. Kafka agit comme un buffer géant : il absorbe les pics de charge et retient les données en sécurité jusqu'à ce que les Consumers soient prêts.

08 — Implémentation

Producer Python — Script d'Ingestion Local (MOCK)

En avance sur le planning, nous avons développé le script Python d'ingestion qui lit les deux fichiers sources et simule un flux de données en temps réel. Ce script constitue la base du Producer Kafka : il sera connecté au Broker lors du Sprint 2 via la bibliothèque kafka-python.

Le script est structuré en deux phases distinctes, reflétant exactement l'architecture pipeline définie dans ce rapport.

🏢
PHASE 1 — BATCH
Lecture complète de business.json
118 MB — ligne par ligne — sans surcharge RAM
💬
PHASE 2 — STREAMING
Simulation live de mock_review.json
100 lignes — pause 0.5s/événement — time.sleep()
producer_mock.py
Python 3.x Offline Mock 
# ===========================================================================
# CONFIGURATION DES FICHIERS SOURCES
# ===========================================================================
import json   # Bibliothèque pour manipuler les données au format JSON
import time   # Bibliothèque pour gérer le temps (utilisée pour la simulation)

# Les chemins vers nos fichiers de données.
# Ces fichiers doivent être dans le même dossier que ce script Python.
business_file    = 'yelp_academic_dataset_business.json'
review_mock_file = 'mock_review.json'

print("🚀 DÉMARRAGE DE L'INGESTION DES DONNÉES (OFFLINE MOCK)\n" + "="*50)

# ===========================================================================
# PHASE 1 : INGESTION DU FICHIER BUSINESS (Mode Batch)
# ===========================================================================
# Objectif : Lire la liste des entreprises (businesses).
# C'est un fichier de 118 MB — la lecture sera très rapide.
print("\n🏢 PHASE 1 : Lecture du fichier Business...")

try:
    business_count = 0  # Compteur pour savoir combien d'entreprises on a lu

    # On ouvre le fichier en mode lecture ('r').
    # L'utilisation de "with open" garantit la fermeture automatique du fichier.
    with open(business_file, 'r', encoding='utf-8') as f_biz:

        # ⚡ Astuce Big Data : Lecture LIGNE PAR LIGNE avec une boucle "for".
        # On évite f_biz.read() qui chargerait tout en RAM (118 MB → saturation).
        for line in f_biz:
            # On convertit la ligne textuelle en objet JSON (Dictionnaire Python)
            business = json.loads(line)
            business_count += 1

            # Pour ne pas polluer le terminal, on affiche uniquement les 5 premiers.
            # (Dans la version Kafka, on enverra tout sans print)
            if business_count <= 5:
                nom     = business.get('name')
                ville   = business.get('city')
                etoiles = business.get('stars')
                print(f"   ✅ [Business {business_count}] {nom} | Ville: {ville} | ⭐ {etoiles}")

    print(f"✔️ SUCCÈS : {business_count} entreprises lues avec succès !")

except FileNotFoundError:
    # Si le fichier n'est pas dans le dossier, on attrape l'erreur proprement.
    print(f"❌ Erreur : Le fichier '{business_file}' est introuvable.")
except Exception as e:
    print(f"❌ Erreur inattendue (Business) : {e}")


# ===========================================================================
# PHASE 2 : INGESTION DES REVIEWS (Mode Streaming / Simulation Temps Réel)
# ===========================================================================
# Objectif : Lire notre échantillon (MOCK) de 100 lignes et simuler un flux continu.
print("\n💬 PHASE 2 : Streaming des Reviews (Simulation Live)...")

try:
    # Même principe : ouverture sécurisée et lecture ligne par ligne
    with open(review_mock_file, 'r', encoding='utf-8') as f_rev:

        for line in f_rev:
            # Transformation en objet JSON
            review = json.loads(line)

            # Extraction de quelques champs intéressants pour l'affichage
            review_id = review.get('review_id')
            stars     = review.get('stars')
            date      = review.get('date')

            # Affichage comme si la donnée venait d'être générée en direct
            print(f"   🔄 [NOUVEL AVIS] 📅 {date} | ⭐ {stars} étoiles | 🆔 {review_id}")

            # 🎭 SIMULATION DE STREAMING :
            # Pause de 0.5 seconde pour imiter des données qui arrivent au compte-gouttes.
            # → Sprint 2 : ce time.sleep() sera remplacé par producer.send(topic, value=...)
            time.sleep(0.5)

    print("\n✔️ SUCCÈS : Fin du flux de données MOCK.")

except FileNotFoundError:
    print(f"❌ Erreur : Le fichier '{review_mock_file}' est introuvable.")
except Exception as e:
    print(f"❌ Erreur inattendue (Reviews) : {e}")

# Fin du programme
print("\n" + "="*50 + "\n🏁 PIPELINE D'INGESTION (TEST LOCAL) TERMINÉ.")
✅ DÉCISION TECHNIQUE
Lecture ligne par ligne avec for line in f — évite de charger 5+ GB en RAM.
🔒 ROBUSTESSE
Blocs try/except avec FileNotFoundError — pas de crash brutal en cas de fichier manquant.
🎭 SIMULATION STREAMING
time.sleep(0.5) simule l'arrivée d'événements au compte-gouttes — sera remplacé par producer.send().
🔄 PRÊT POUR KAFKA
Structure identique au Producer Kafka final — seul le print() sera remplacé par l'envoi au Broker.

Évolution vers le Mode KRaft (Kafka Raft)

Pour le Sprint 2, nous avons fait évoluer notre infrastructure locale en adoptant le mode KRaft (Kafka Raft Metadata). Ce choix architectural majeur élimine totalement la dépendance à Apache Zookeeper, rendant notre pipeline d'ingestion plus léger, plus stable et plus moderne sur nos machines locales.

# ===========================================================================
# ENVIRONNEMENT LOCAL KAFKA (MODE KRAFT)
# ÉQUIPE SE2 - PROJET BIG DATA (YELP DATASET)
# ===========================================================================
# Ce fichier déploie Kafka et inclut la configuration réseau exacte (Listeners)
# pour permettre à Kafka UI (dans Docker) et au script Python (sur l'ordinateur)
# de communiquer avec Kafka en même temps.

version: '3.8'
services:

  # ---------------------------------------------------------
  # SERVICE 1 : BROKER KAFKA (Le Serveur Principal)
  # ---------------------------------------------------------
  kafka:
    image: confluentinc/cp-kafka:latest
    container_name: kafka_se2
    ports:
      # Port EXTERNE (9092) : Utilisé par notre script Python (localhost)
      - "9092:9092"
    environment:
      # Activation du mode KRaft (Broker et Contrôleur fusionnés)
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_NODE_ID: 1
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093

      # =========================================================
      # 🔑 LE SECRET EST ICI : LA CONFIGURATION DES PORTES (LISTENERS)
      # =========================================================
      # On définit 3 réseaux/portes de communication pour éviter les conflits :
      # - INTERNAL   : Porte pour les conteneurs Docker (comme Kafka-UI)
      # - EXTERNAL   : Porte pour l'ordinateur hôte (Notre script Python)
      # - CONTROLLER : Porte pour la gestion interne de Kafka (KRaft)
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT

      # On associe chaque porte à un port spécifique dans le conteneur
      KAFKA_LISTENERS: INTERNAL://0.0.0.0:29092,EXTERNAL://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093

      # On dit aux clients quelle adresse exacte utiliser :
      # - Kafka UI (DANS Docker) → kafka:29092
      # - Python   (HORS Docker) → localhost:9092
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:29092,EXTERNAL://localhost:9092

      # Précise quelle porte les brokers utilisent pour communiquer entre eux
      KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL

      # Précise quelle porte est réservée au contrôleur KRaft
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER

      # Configuration standard pour un cluster à un seul nœud
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      CLUSTER_ID: 'MkU3OEVBNTcwNTJENDM2Qk'

  # ---------------------------------------------------------
  # SERVICE 2 : KAFKA UI (Interface Web de Suivi)
  # ---------------------------------------------------------
  kafka-ui:
    image: provectuslabs/kafka-ui:latest
    container_name: kafka_ui_se2
    ports:
      # Interface accessible via http://localhost:8080
      - "8080:8080"
    environment:
      - KAFKA_CLUSTERS_0_NAME=Cluster_Local_SE2
      - KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS=kafka:29092
    depends_on:

      - kafka
S2 · 03 — Producer Final

Script Producer Final — Intégré avec Kafka

Le script Python a été mis à jour pour passer de la simulation locale (Sprint 1) à une ingestion active vers le topic Kafka. La différence clé : le time.sleep() et le print() sont remplacés par producer.send(). La sérialisation JSON encode chaque ligne en bytes avant l'envoi.

⬅ SPRINT 1 (Local)
print(f"🔄 {review_id}")
time.sleep(0.5)
→
SPRINT 2 (Kafka) ➡
producer.send(
  'topic_reviews',
  value=review
)
producer_final.py
kafka-python Production Ready 
# ===========================================================================
# PRODUCER FINAL SE2 : INGESTION YELP DATASET → KAFKA
# ===========================================================================
import json
import time
from kafka import KafkaProducer

# ---------------------------------------------------------------------------
# CONNEXION AU BROKER LOCAL
# Utilisation de 127.0.0.1 (au lieu de localhost) pour la stabilité sous Ubuntu.
# Le listener EXTERNAL du docker-compose mappe ce port vers kafka:9092.
# ---------------------------------------------------------------------------
producer = KafkaProducer(
    bootstrap_servers=['127.0.0.1:9092'],
    # Sérialisation JSON : chaque message Python (dict) est encodé en bytes UTF-8
    # avant d'être envoyé dans le topic. Kafka ne transporte que des bytes.
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)

# ---------------------------------------------------------------------------
# PHASE 1 — BATCH : Ingestion du fichier Business complet
# ---------------------------------------------------------------------------
print("🏢 PHASE 1 : Envoi des données Business vers Kafka...")
with open('yelp_academic_dataset_business.json', 'r') as f:
    for line in f:
        business = json.loads(line)
        # Envoi vers le topic 'topic_business' — valeur sérialisée automatiquement
        producer.send('topic_business', value=business)

# flush() : attend que TOUS les messages soient réellement envoyés au broker
# avant de fermer la connexion. Garantit l'intégrité du batch.
producer.flush()
print("✔️ Business : envoi batch terminé.")

# ---------------------------------------------------------------------------
# PHASE 2 — STREAMING : Ingestion du Mock Review (100 lignes)
# Simule un flux temps réel à partir de notre échantillon de test.
# ---------------------------------------------------------------------------
print("\n💬 PHASE 2 : Streaming des Reviews vers Kafka...")
with open('mock_review.json', 'r') as f:
    for line in f:
        review = json.loads(line)
        # Envoi vers le topic 'topic_reviews'
        producer.send('topic_reviews', value=review)
        # Pas de time.sleep() ici : Kafka gère naturellement le débit

# flush() final : garantit l'envoi de tous les messages en attente
producer.flush()
print("✔️ Reviews : fin du flux. 100 messages envoyés.")
print("\n🏁 PIPELINE D'INGESTION KAFKA TERMINÉ.")

S2 · 06 — Analyse

Justification des Choix Techniques

⚡
KRaft vs Zookeeper

KRaft réduit la consommation RAM et simplifie la communication réseau entre les conteneurs Docker. Sur nos machines locales (8-16 GB RAM partagée avec le système, l'IDE et d'autres processus), l'élimination d'un second processus Zookeeper est critique. De plus, KRaft est le standard officiel depuis Kafka 3.3 — Zookeeper est déprécié et sera retiré dans les futures versions.

🖥️
Kafka UI — Monitoring Visuel

Choisi pour monitorer visuellement les flux et vérifier que les messages arrivent en temps réel sans avoir à utiliser le terminal CLI (commandes kafka-console-consumer complexes). L'interface affiche en temps réel le nombre de messages, les offsets, les consommateurs actifs et les statistiques de chaque topic — indispensable pour valider nos tests sans expertise Kafka avancée.

💾
Rétention Log — Clean Up Policy: DELETE

Indispensable pour traiter le fichier review.json de 5,34 GB lors du Sprint 3. La politique DELETE supprime automatiquement les segments anciens selon une durée ou taille configurée, ce qui permet de tester le pipeline complet sans risque de saturer l'espace disque de nos machines locales. Sans cette politique, Kafka accumulerait les logs indéfiniment.

🔒
Sérialisation JSON + 127.0.0.1 vs localhost

La sérialisation json.dumps().encode('utf-8') convertit chaque dict Python en bytes — le seul format que Kafka peut transporter. L'utilisation de 127.0.0.1 au lieu de localhost évite les problèmes de résolution DNS sous Ubuntu où localhost peut pointer vers IPv6 au lieu d'IPv4, causant des erreurs de connexion.
